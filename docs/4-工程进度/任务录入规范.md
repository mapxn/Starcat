# Starcat 任务录入规范

> 适用范围：Multica `Starcat` 项目（`project_id = 4739d7e5-194c-481f-a7ce-63d31a796435`）的 issue 创建与梳理。
>
> 维护者：dong4j  
> 创建：2026-06-06

本规范定义任务的**标题格式、详情字段、状态默认值、CLI 创建方式与给 AI agent 的 system prompt**。所有人/agent 在本项目下创建或整理 Multica 任务时必须遵循。

## GitHub 与 Multica 对齐及收尾

2026-10-07 起，Starcat 主仓库及配套仓库均以 Multica 为日常执行入口。每个在办 Multica 任务必须对应一张 GitHub Issue，GitHub 正文记录相同 HOM 编号；配套仓库任务链接到其所属仓库，不能只凭裸 `#数字` 判断身份。

### 录入和范围变更

1. 完整读取双方待办后匹配已有任务；单边缺失才补录，不能恢复已完成或明确取消的历史范围。
2. Multica 描述开头写完整的 GitHub 主关联 URL，并在末尾增加“GitHub 关联与双端收尾”。其他 Issue 链接必须说明是父子依赖、来源或取消记录。
3. GitHub 使用英文标题、范围和验收清单；Multica 保留中文任务说明及同一验收范围。后续修改范围时同时更新双方，不能只修改一端。
4. 父任务与子任务分别对应独立 Issue。子任务完成只关闭自己的主关联；父任务须等保留子项与父任务自身验收全部通过。
5. 新镜像统一为未排期任务，不因补录而分配 agent、提高优先级或声称功能尚未实现；开工前仍须核对现有实现及验收证据。
6. Multica 分页读取直到 `has_more = false`；服务端单页最多 100 条，不能用 `--limit 200` 代替完整翻页。

关联标记使用以下格式；HOM 编号和完整 URL 必须与当前任务一致：

```text
<!-- starcat-tracker:v1 {"multica":"HOM-xxx","github":"https://github.com/OWNER/REPO/issues/NUMBER"} -->
```

### 完成和取消

| Multica 结果 | GitHub 结果 | Project 结果 |
| --- | --- | --- |
| `done`（已验收） | `closed` / `completed` | `Done` |
| `cancelled`（不再处理） | `closed` / `not planned` | `Done` |
| 其他在办状态 | `open` | 保持对应排期/执行阶段 |

执行者完成任务时必须：

1. 核对主关联的仓库、编号及验收标准，在双方记录实际 commit/PR、验证结果和限制。未验收的实现不能直接标为完成。
2. 在该 GitHub Issue 添加英文收尾说明，使用 `gh issue close NUMBER --repo OWNER/REPO --reason completed` 关闭，并同步 GitHub Project；取消则使用 `--reason 'not planned'`。
3. 回读 GitHub 的 `state` / `stateReason` 及 Project 状态，确认后把本 Multica 任务更新为 `done` 或 `cancelled`，再回读状态。若已通过 PR 自动关闭，验证关闭原因及证据即可，不重复发表评论。
4. 任一端失败时，在可用的一端明确记录“同步待补”及失败步骤，不宣称双端完成；恢复后先回读再补写，避免重复评论或误关其他 Issue。
5. 若 Multica 已被人工标为完成，仍需核对交付证据并补齐 GitHub；不能仅凭状态跳过验收。

提交标题遵循所属仓库的 Git 提交规范，HOM 编号及 GitHub URL 放正文/Footer 或 PR 描述。主仓库保持 `<type>(<scope>): <中文摘要>`，不再要求以 `[HOM-xxx]` 替代规范标题。

**能力边界**：以上是 agent/人工执行流程。本次未配置 Multica 状态变化 webhook 或定时自动关闭任务；仅在界面点击 `done` 不会自动向 GitHub 发请求。

当前对应关系见 [2026-10-07-GitHub与Multica任务对齐](2026-10-07-GitHub与Multica任务对齐.md)。本节同样适用于下方录入示例及 system prompt。

## 一、标题规范

### 1.1 格式

```
[一级]:[二级] 简洁任务标题
```

- `[一级]` 与 `[二级]` 都用半角中括号；`:` 用半角冒号；冒号两侧不留空格。
- 二级与正文之间空一格。
- 任务标题用陈述句，不加句号，不加 emoji。
- 标题总长建议 ≤ 30 字（一级 + 二级 + 标题），超过时要么拆分，要么去掉可省略的修饰词。

### 1.2 一级分类（必须从下面 5 类选一个）

| 一级 | 含义 | 是否允许改代码 |
| --- | --- | --- |
| `[Feature]` | 新增功能 | 允许 |
| `[BUG]` | 问题修复 | 允许 |
| `[优化]` | 已有功能的体验 / 性能 / 视觉迭代（非 bug） | 允许 |
| `[调研]` | 仅做技术调研 | **不允许改代码**，只能新增 / 修改文档 |
| `[文档]` | 仅做文档同步 / 重写 / 归档（非调研） | **不允许改代码**，只能改文档 |

> 一级分类必须严格控制为这 5 类。如果你判断现有 5 类都不能描述，必须先与 dong4j 对齐再使用新的一级，不允许私自扩展。

### 1.3 二级分类（按业务模块）

当前 Starcat 在用的二级清单（请优先复用，避免出现 `[搜索]` / `[Search]` / `[全局搜索]` 这种同义异名）：

```
基础设施 / 安全：[安全] [认证] [订阅] [发布] [官网] [国际化] [效率]
核心业务：[搜索] [Discover] [安全雷达] [健康度] [贡献机会] [技术选型] [开源工具]
UI 与导航：[导航] [列表] [Sidebar] [详情页] [UI]
跨端与同步：[同步] [多端] [导入导出] [AI整理] [AI高级]
工程治理：[路线对齐] [设计同步] [Phase2]
```

> 新增二级前，先 `multica issue list --project 4739d7e5-194c-481f-a7ce-63d31a796435 --limit 100 --offset 0 --output json` 并按 `has_more` 翻完所有页，检查是否存在等价二级；命名要稳定。

### 1.4 反例

```
❌ 优化下设置页                            # 缺一二级分类
❌ [feature]:[ui] 调整间距                 # 大小写不规范，且太空泛
❌ [Feature]:[搜索] / [优化]:[搜索] 双任务  # 同一改动不要分裂成两个不同一级
❌ [Bug] 修复                              # 一级名错（应为 [BUG]）

✅ [Feature]:[搜索] 结构化搜索页
✅ [BUG]:[列表] 状态过滤下详情页改状态后列表不刷新
✅ [调研]:[健康度] OpenSSF Scorecard 接入评估
```

## 二、详情模板

每个任务的 `description` 必须包含下面 **7 个必填 H2 字段**，**顺序固定，标题级别用 `##`**，缺一不可。空字段用 `_无_` 占位，不允许整段省略。正文开头给 GitHub 主关联，末尾追加“GitHub 关联与双端收尾”；必要时附原始详细范围。

```markdown
## 背景

<2~6 行：现状、为什么要做、不做的代价。必须引用至少 1 个文档章节或代码路径，避免凭空立项。>

## 需求故事

<以"作为 ... / 我希望 ... / 这样我能 ..."的句式给出 1~3 个角色视角。至少要有"目标用户视角"和"开发者视角"。>

## 任务说明

<编号列表，按"做什么、按什么顺序、与谁协作"的粒度拆。每条 1 句话，可读完即知道动作。>

1. ...
2. ...
3. ...

## 关联文档

- `docs/xxx.md` §x.y
- 父 / 子 / 兄弟任务：`[Feature]:[xxx] yyy`（HOM-xxx）
- 关键代码路径：`Starcat/Features/xxx/yyy.swift`

## 测试约束

<列出测试设备、必须覆盖的边界、单测/集成测/手测的最小集合。强调"哪些事情禁止做"。>

- 测试设备：...
- 必须覆盖：...
- 禁止：...

## 验收标准

<勾选清单，每条都要可机械验证。避免"体验良好""界面美观"这种主观描述。>

- [ ] ...
- [ ] ...
- [ ] PR 描述中包含本任务 ID

## 提交规范

- Commit 标题遵循所属仓库规范，正文/Footer 关联本任务实际 HOM 编号和 GitHub URL
- <其他特殊约定，例如：私钥不入仓 / 文档放某目录 / 改动需 dong4j review>
```

### 2.1 字段编写约束

| 字段 | 必须 | 长度参考 | 关键约束 |
| --- | --- | --- | --- |
| 背景 | ✅ | 2~6 行 | 必须引用 ≥ 1 个文档或代码路径 |
| 需求故事 | ✅ | 1~3 个角色 | 必须有"目标用户" + "开发者"双视角 |
| 任务说明 | ✅ | 3~10 条 | 每条 1 句话，可读完即知动作 |
| 关联文档 | ✅ | 3~8 条 | 至少 2 条文档 + 1 条代码路径 |
| 测试约束 | ✅ | 3~8 条 | 必须明确"禁止做什么"（写约束才有约束） |
| 验收标准 | ✅ | 3~8 条 | 每条可机械验证；最后一条固定为 "PR 描述含任务 ID" |
| 提交规范 | ✅ | 1~3 条 | 标题遵循仓库规范，正文/Footer 关联 HOM 编号和 GitHub URL |

### 2.2 状态与负责人

- 新建任务**统一 `--status backlog`**（不要默认 `todo`，否则会被误判为已排期）。
- **不分配负责人**（不传 `--assignee` / `--assignee-id`）。
- 不设 `--priority`，优先级由后续排期决定。

## 三、CLI 创建方式

### 3.1 强制使用 `--description-stdin` + 引号 HEREDOC

description 含 Markdown 反引号、`$`、换行；inline `--description` 在 shell 里会被反复转义出错。**统一用引号 HEREDOC**，不要用单行 `--description`。

```bash
multica issue create \
  --title "[Feature]:[<二级>] <标题>" \
  --status backlog \
  --project 4739d7e5-194c-481f-a7ce-63d31a796435 \
  --output json \
  --description-stdin <<'DESC'
## 背景

<...>

## 需求故事

作为 <角色>，我希望 <动作>，这样我能 <价值>。
作为 dong4j（开发者），我希望 <动作>，这样我能 <价值>。

## 任务说明

1. <...>
2. <...>
3. <...>

## 关联文档

- `docs/<...>.md` §<...>
- 关键代码路径：`Starcat/<...>.swift`

## 测试约束

- 必须覆盖：<...>
- 禁止：<...>

## 验收标准

- [ ] <...>
- [ ] PR 描述中包含本任务 ID

## 提交规范

- Commit 标题遵循所属仓库规范，正文/Footer 关联本任务实际 HOM 编号和 GitHub URL
DESC
```

> 注意 `<<'DESC'` 的单引号——它告诉 shell **不要扩展**反引号、`$`、`$()`，否则 description 会被 shell 提前求值。

### 3.2 创建前必查清单

- [ ] `multica issue list --project 4739d7e5-194c-481f-a7ce-63d31a796435 --limit 100 --offset 0 --output json`，按 `has_more` 读取全部页，并核对 GitHub 对应仓库，避免重复创建或恢复已取消范围。
- [ ] 在仓库内 `rg / grep` 验证「背景」与「关联文档」中引用的章节、代码路径**真实存在**，禁止编造。
- [ ] 如果是已验收内容，应按本文件的双端收尾流程关闭已有任务，而不是新建；已有实现但缺验收的，继续核对后再定状态。

### 3.3 后续修改

- 改标题：`multica issue update <id> --title "新标题"`
- 改描述：`multica issue update <id> --description-stdin <<'DESC' ... DESC`
- 改状态：`multica issue status <id> backlog|todo|in_progress|in_review|done|blocked|cancelled`

## 四、给 AI agent 的 system prompt（可直接复用）

下面整段可以直接喂给负责"创建 / 整理 Multica 任务"的 AI agent，获得稳定输出。

```text
你是 Starcat 项目的任务录入助手。请严格按下列规则把用户给出的需求/想法转换为 Multica issue。

【强制规则】

1. 所有任务标题必须遵循 `[一级]:[二级] 标题` 格式：
   - 一级仅允许 5 类：[Feature] / [BUG] / [优化] / [调研] / [文档]
     · [调研] 与 [文档] 不允许改代码，只允许改/新增文档
   - 二级使用现有业务模块名（先用 `multica issue list --project <pid>` 查一遍，复用已有的）
   - 二级与正文之间空一格，冒号用半角，不加 emoji，不加句号
   - 标题总长 ≤ 30 字

2. description 必须用以下 7 个必填 H2 字段，顺序固定，缺一不可：
   ## 背景            →  必须引用 ≥ 1 个文档章节或代码路径
   ## 需求故事        →  含"目标用户"与"开发者"双视角
   ## 任务说明        →  3~10 条编号列表
   ## 关联文档        →  ≥ 2 条文档 + ≥ 1 条代码路径
   ## 测试约束        →  必须含"禁止做什么"
   ## 验收标准        →  勾选清单，最后一条必须是 "PR 描述中包含本任务 ID"
   ## 提交规范        →  标题遵循仓库规范，正文/Footer 关联 HOM 编号和 GitHub URL

3. 状态固定 `backlog`；不分配负责人；不设优先级。

4. 创建命令统一使用 `--description-stdin` + 引号 HEREDOC，禁止 inline `--content` / `--description`：

   multica issue create \
     --title "[一级]:[二级] 标题" \
     --status backlog \
     --project <project-id> \
     --output json \
     --description-stdin <<'DESC'
   ## 背景
   ...
   DESC

5. 创建前必须先做：
   - 用 `multica issue list --project <pid> --limit 100 --offset 0 --output json` 并按 has_more 翻完所有页，同时核对 GitHub 现有任务，避免重复创建
   - 用文档/代码 grep 验证背景与关联文档真实存在，禁止编造
   - 如果是已验收内容，按双端收尾流程关闭已有任务，而不是新建；不能只凭已有代码或单边状态判断完成

6. 双端一致性：
   - 主仓库与配套仓库均一张 Multica 任务对应一张所属仓库的 GitHub Issue
   - Multica 描述开头给完整 GitHub 主关联 URL；GitHub 正文记录 HOM 编号，范围和验收同步维护
   - 验收后在 GitHub 记录英文交付证据，按 completed 关闭并同步 Project，再将 Multica 设为 done，回读双方状态
   - 取消对应 cancelled / not planned；任一端失败记录“同步待补”；子任务完成不能直接关闭父任务
   - 这是执行者收尾流程，不能宣称 Multica 手动点击 done 已安装自动同步

7. 输出格式：
   - 第一行给标题
   - 之后给完整 description 文本（7 个必填 H2 字段，加 GitHub 主关联与双端收尾）
   - 最后给可直接执行的 multica CLI 命令
   - 不要附加寒暄、emoji、与上述结构无关的内容

【输入】用户的需求描述
【输出】严格按上述规则组装的「标题 + description + CLI 命令」三段式结果
```
